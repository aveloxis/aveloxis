# Upgrading

How to move an existing deployment from any earlier release to the
current one — and, just as important, which repairs `aveloxis migrate`
does **not** do for you.

## The four steps

Every upgrade is these four steps, in this order, on the primary host:

```bash
AVELOXIS_SRC=/path/to/aveloxis    # the git checkout of this repository
cd "$AVELOXIS_SRC" && go install ./cmd/aveloxis && aveloxis version   # 1. the new binary (running processes keep the old one until restarted)
aveloxis deploy-checklist --pending   #    every step this database still needs, oldest first, and the migrate for step 3 — read it now, before step 3 moves the stamp
aveloxis stop all                 # 2. nothing runs against the schema while it changes
aveloxis migrate --skip-views     # 3. the schema — a plain `aveloxis migrate` instead when the checklist asks for one (a release that changed a view definition)
#                                 #    …then the checklist's checks, heals and audits, every block's, oldest first
aveloxis ack-deploy               #    …then record that they ran
aveloxis start all                # 4. serve, web and api; then any step the checklist says needs the running release
```

`deploy-checklist --pending` reads this database's last **acknowledged**
deploy and its schema stamp and prints the range `aveloxis start serve`
enforces — the same computation, not a copy of it: every release after the
acknowledged one; from the stamp, its own block included, when no deploy
was ever acknowledged (the stamp release's steps were never acknowledged
either) or when the stamp is *behind* the acknowledgement (one recorded
after a migrate that did not complete — the stamp is the evidence); and the
new binary's own steps when there is neither, or when the acknowledgements
cannot be read, which it says. A database from before v0.29.0 has no
`deploy_ack` table and counts as never acknowledged: its range starts at
the stamp. When the stamp is current and this release's steps are
acknowledged (or it has none), it prints `nothing pending` — only then: a
missing, unreadable or malformed stamp prints the steps, saying why first,
and so does a fresh install with no collected data yet.
Otherwise it ends by naming the migrate step 3 runs. It reads the database in
`aveloxis.json` (`--config` for another) and changes nothing. Versions
compare as numbers (0.29.9 is before 0.29.10).

When more than one release in the range has deploy steps, `deploy-checklist
--pending` (and `--since`) prints a header before the blocks: stop, migrate and start **once**,
not once per block, with the strongest migrate any block asks for (a plain
`aveloxis migrate` if any block needs it and no later release in the range
lifts it — 0.29.61 lifts 0.29.60's, for example, because it moved the
supply-chain views out of the 8Knot batch — otherwise `--skip-views`) —
that is the migrate step 3 runs, and the one the start gate's refusal names.
When the header names `--skip-views` although an older block in the range
asks for a plain migrate, a line under it says which later release lifts
that block's instruction.
The header's sequence ends with `aveloxis ack-deploy`, then `aveloxis start
all`, as the steps above do. Consecutive releases with identical steps print as
one block labelled with the range they cover. Each block's own stop, migrate
and start lines are covered by the four steps; its checks, heals and audits
are not, and run in step 3, oldest first; a step that needs the running
release (such as `adopt-forge-id` or the approvals page) runs after step 4.
A `--since` value that is not a version (dotted numbers such as `0.29.64`)
is an error and exits non-zero, rather than printing an empty list.

`aveloxis ack-deploy` belongs to step 3. When the new binary's release has
deploy steps, `aveloxis start serve` (and `start all`) asks at a terminal
whether they were completed and, without a terminal — a script, systemd,
an SSH command — **refuses to start** until they are acknowledged. Run it
after the heals, not before: it records that the steps ran. The gate is
`aveloxis start`'s: a systemd unit runs `aveloxis serve` directly, which
migrates at its own start with no gate, so under systemd run the ladder
by hand and start the target last ([Production Deployment](deployment.md#11-upgrading)). If the schema
stamp cannot be read, `--pending` says so and starts the range from the
acknowledgements (the new binary's own steps if there are none); the
section below says how to find the version you are
coming from, and `aveloxis deploy-checklist --since <version>` prints the
steps after it.

`--skip-views` skips only the 8Knot materialized-view batch (hours at
fleet scale); everything else — the schema, the ledgered backfills, the
two supply-chain views — runs either way (v0.29.61). `aveloxis
refresh-views` is not one of the four steps: a release whose heals fed a
materialized view lists it in its own checklist (the "standard ladder"
below shows where it sits when a release asks for it). Since v0.29.68 `web`,
`api` and the scancode worker **refuse to start** while the schema stamp
is behind their binary, naming the migrate, instead of serving queries
against columns the schema does not have yet; and `aveloxis start serve`
prints the deploy steps of every release since the last acknowledged one,
oldest first, under the same once-only header and with the same collapsing
of identical blocks as `deploy-checklist --pending`, not only the current
version's. Neither web nor api ever migrates. The
sections below are the detail behind step 3.

## The two halves of an upgrade

1. **`aveloxis migrate`** applies every schema change and every one-shot
   SQL backfill between your old version and the new one. It is
   idempotent and safe to re-run. Since v0.28.4 the expensive one-shot
   data steps record their completion in
   `aveloxis_ops.migration_ledger`, so a later migrate is seconds — only
   the first migrate across a large version gap pays the full walk.
2. **Operator-run heal commands** repair data the migrate cannot: they
   call the GitHub/GitLab APIs, run for hours at fleet scale, or need a
   judgment call (merging duplicate repositories, for example). They are
   deliberately *not* migrations. The table further down lists every one
   with the release that introduced it, so you can skip the ones that
   predate the version you are coming from.

Find the version you are coming from before you start — it decides
which rows of that table apply:

```sql
SELECT schema_version FROM aveloxis_ops.schema_meta;
```

If that fails with `relation "aveloxis_ops.schema_meta" does not exist`,
the database predates v0.14.5 (the release that introduced the stamp).
Every row of the table below applies to it — the earliest entry is
v0.23.6 — so you do not strictly need the exact version, but the binary
that last wrote data tells you where you were: `aveloxis serve` migrates
at startup, so the newest `tool_version` on collected rows is the last
binary that migrated the schema:

```sql
SELECT tool_version
FROM aveloxis_data.repo_info
ORDER BY data_collection_date DESC NULLS LAST, repo_info_id DESC
LIMIT 1;
```

## The standard ladder

```bash
AVELOXIS_SRC=/path/to/aveloxis   # the git checkout of this repository
cd "$AVELOXIS_SRC" && go install ./cmd/aveloxis
aveloxis version                # confirm the new binary
aveloxis deploy-checklist --pending   # the exact steps this database needs: follow them where they differ from these
aveloxis stop all               # serve, web, api (also cleans stale pidfiles)
aveloxis migrate --skip-views   # schema + ledgered backfills; skips the materialized views
# ... operator-run heals from the table below, in order ...
aveloxis refresh-views          # refresh the materialized views' data (--set 8knot or supply-chain for one set; add --aggregates for the dm_ tables; slow)
aveloxis ack-deploy             # record that the steps ran; a non-interactive `start serve` refuses without it
aveloxis start all
```

`refresh-views` refreshes each view's **data**; it does not change a view's
**definition**. A release that changes a view definition needs one plain
`aveloxis migrate` (without `--skip-views`), which drops and re-creates the
views from the new definitions; `serve` never does it at startup. v0.29.57 is
such a release (`explorer_libyear_summary`'s definition now orders unknown
repositories last): its deploy checklist (in the range `aveloxis deploy-checklist --pending` prints) uses a
plain `aveloxis migrate` in place of the `--skip-views` step above, then
checks that the new definition is in place. That check matters because the
migrate only logs a WARN (`materialized view creation had errors`) when the
views fail to re-create, and still exits 0 with the old definitions in place.
Since v0.29.68 the build enforces the rule: `matviews.sql` is pinned by
digest, and a change to it fails the test suite until the release shipping
it is named and that release's checklist carries the plain migrate.

Run `aveloxis migrate` explicitly rather than letting `aveloxis serve`
migrate at startup: `web` and `api` never migrate and (since v0.29.68)
refuse to start while the schema stamp is behind their binary, and (since v0.27.131) `serve` trusts the
schema-version stamp and skips the migration walk entirely once it
matches — so after any *hand* edit to the schema, run `aveloxis migrate`
once. Verify the stamp matches the binary afterwards:

```sql
SELECT schema_version FROM aveloxis_ops.schema_meta;   -- equals `aveloxis version`
```

## What to watch for in the migrate output

**0.29.211 is the fixes from the fourth review; no schema change and no configuration change.** What changes on a fleet:

- **A Maven build whose imported BOM cannot be obtained stays "not whole"**, whatever else its poms hold and in whatever order they are read. (0.29.210, which no fleet ran, judged such a pom whole once it had two dependencies with no version.)
- **Large honest builds are read.** A Maven reactor whose parent manages its own modules by reference, and a Gradle build whose modules share a large applied script, were refused by 0.29.210's bounds. The bound on a whole Gradle tree is ten times the bound on one file: a deliberately pathological tree can hold one worker for about three minutes per 8 MiB of Gradle files before the rest are reported unreadable.
- **Memory while reading a build** no longer grows with modules times imports, or with directories times shared scripts.
- **More manifest forms are read:** one-line Gemfile blocks with several gems, an `else` arm, `gem(...)` or a modifier after `end`; a `pubspec.yaml` dependency written as a block with its version on its own line. A `mix.exs` comment after a dependency no longer ends up in its version.
- **The migrate** quotes the table names in its tool-version defaults and deferrable-constraint statements. The statements are otherwise the same.

**0.29.210 is the fixes from the third review; no schema change and no configuration change.** What changes on a fleet:

- **Memory while reading a large build.** Reading a Maven or Gradle build holds memory in proportion to the files read. (0.29.209, which no fleet ran, held a copy of the managed-version table per module.)
- **A build file that costs too much to read costs itself.** One pathological `pom.xml` no longer makes the repository's other poms unreadable. A whole tree whose Gradle files cost more than their size allows in total stops being read; each file not read is reported by name as a manifest that could not be read.
- **After an upper bound, only a real bound supplies a version.** A number in a trailing comment does not (`foo: '<2.0.0' # pinned until 3`), and an alternative (`||`, or hex's `or`) ends the range.
- **A gem declared on one line inside a block** (`if ... then gem ... end`, `group ... do gem ... end`) is read.
- **A Maven coordinate that cannot be asked for** is recorded as not found, as a version range is, and counted in the log line as `coordinates_not_askable`.
- **A repository host** written as an IPv4 address in its IPv6-mapped form is the same host as the IPv4 address.

**0.29.209 is the fixes from the second review; no schema change and no configuration change.** What changes on a fleet:

- **An upper bound or an exclusion alone gives no version.** A dependency declared only as `<X`, `<=X` or `!=X` (`rich = "<13.5.0"`, `tensorflow <=1.14`, `tokenizers = "!=0.12.0"`) was recorded as using `X`: the version the line excludes, or one it merely allows. Its row now has no version, and from the next analysis and scan its findings are "version not determined". A range with a floor or a pin anywhere in it (`<3,>=2.1`) uses that. This is every reader that takes a version from a requirement: Python, Ruby, Dart, Elixir, Composer, Cargo, npm.
- **A Go dependency** whose `go.mod` version is not a version (a templated `go.mod`) is "version not determined" too.
- **Declared Maven repositories:** one lookup consults at most 32 of them (with `declared_repository_fetch` off none is asked, and the same 32 are the ones looked up among stored answers), and a request to one is cut off when the analysis's five minutes for them end.
- **A repository host has one spelling** however its port or an IPv6 address is written. A distrust covers a host on one port.
- **Build files that cost too much to read.** A `pom.xml` or Gradle build that costs far more to read than its size allows, or that depends on a settings file, parent build, applied script or version catalogue that could not be read, shows as a manifest that could not be read. The log names the file.
- **Registry sources.** A Gemfile dependency whose source is rubygems.org, and a `pubspec.yaml` dependency hosted on pub.dev, are registry dependencies; so is a `mix.exs` dependency with a source option only in a comment. (0.29.208, which no fleet ran, marked all three as not from a registry.)
- **Fleet package pages** log one WARN per supply-chain view when a view lacks a column this release reads (it was built by an earlier release and not rebuilt) and they read live instead. Run `aveloxis migrate`.

**0.29.208 is the fixes from the first review of that program; no schema change and no configuration change.** What changes on a fleet:

- **A dependency with no version is always "version not determined".** Until now a dependency with no version whose requirement text held a digit (the package's own name: `jinja2`, `boto3`, `log4j-core`) or only an upper bound (`tensorflow<2.0`) was counted as exposure at a known version, with every advisory its package has ever had. At each repository's next scan those findings move to "version not determined". None is deleted. The exposure counts of the repositories that had them go down.
- **A declared Maven repository gets none of your trust.** The hosts and address ranges you trust (your forge instances, your configured repositories, `collection.private_network_hosts`) no longer apply to a repository that a collected build file declares. Before, a build file that named one of those hosts was fetched from. One analysis also waits on declared repositories for five minutes in all; past that it uses what is stored and records the rest as not known.
- **A repository host is spelled with its port.** If `collection.maven_repositories` holds a URL with a port other than 443, the Repository hosts page lists that host with its port. A distrust recorded for the name without the port never took effect and does not cover it: distrust the host again on that page if you meant to.
- **Restoring a distrusted host deletes anything stored from it first.**
- **A new coverage state**, "sent for checking; no complete answer came back" (`no_answer`), for a scan whose every query OSV refused or cut short. It read "no dependency could be sent for checking". A repository for which nothing has recorded what it depends on now shows a dash for its count, not 0.
- **Dependencies from a path, a git repository, an SDK or another server** in `pubspec.yaml`, `mix.exs`, `Gemfile`, `go.mod` (a `replace` by a local path) and `composer.json` are no longer treated as the registry's package of that name. They leave the libyear table and are not sent to OSV; open findings on them close at the next scan.
- **Haskell `package.yaml`**: the entries of `default-extensions`, `exposed-modules` and `ghc-options` are no longer stored as dependencies.
- **A Maven or Gradle build file over 8 MiB**, or a Gradle file that costs far more to read than its size allows, shows as a manifest that could not be read.
- **Packagist publishers** whose package is named `owner/repo`, and **Hackage publishers**, are asked about their own package.
- **API clients**: `counts.resolved_unlabelled_other` (introduced in 0.29.196, which no release shipped) is `counts.resolved_other_reason`, always present.

**0.29.207 is the release of the vulnerability and dependency program's first part (0.29.147 to 0.29.207), deployed as one.** `aveloxis deploy-checklist --pending` prints one block for the whole range: a release whose steps and notes the next release contains is no longer printed on its own. The block's start step begins with a summary of the whole deploy; the entries below this one say what each version in the range changed.

**0.29.206 asks about Bioconductor packages and about a CRAN publisher's own package; no migrate step.** At its next scan, a repository whose `renv.lock` names Bioconductor packages has each asked of OSV by name and version (OSV holds no Bioconductor advisory yet, so nothing is found until one is filed), and a repository that publishes a package to CRAN, or a Swift package, is asked about that package, as publishers to other registries already are.

**0.29.205 reads `renv.lock`; no migrate step.** A repository with a `renv.lock` gets its R packages' exact versions at its next analysis: the packages the file says are from CRAN are checked against OSV's CRAN advisories at those versions; Bioconductor packages are recorded under their own ecosystem; packages from a forge, a URL or a private repository are left out and counted in the log.

**0.29.204 reads R packages; no migrate step; one new outbound host.** A repository with an R `DESCRIPTION` gets inventory rows for its dependencies at its next analysis (package manager `cran`, purl `pkg:cran/<name>@<version>`), with libyear and licence from `crandb.r-pkg.org`, and those dependencies are checked against OSV's CRAN advisories at its next scan. If outbound traffic is filtered, allow `crandb.r-pkg.org` over HTTPS; without it R dependencies keep their rows and read "lookup failed; it is asked again".

**0.29.201 reads every OSV answer to its end; no migrate step; the default of one setting changes.** `collection.osv_pages_per_query` now defaults to `0`, no cap (it was a provisional 10 from 0.29.169). A long answer, which is what a dependency with no declared version or a GitHub Action gets, is read whole, so no repository reads "scanned; some packages not fully checked" because of a page cap. A scan of such a repository makes more requests to OSV than before. Each scan's summary log line carries `osv_longest_answer_pages`; if you want a cap, choose it from that. A configuration that sets the value keeps it. A fleet already running 0.29.200 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.200 shows the coverage state on the web GUI's repository page and on the showcase; no migrate step, no setting.** The repository page's Vulns tile shows the coverage state under its count, a dash where a 0 would claim a check that did not happen, "version not determined" in place of "version unknown", and "unavailable" (not 0) on any tile whose statistics could not be read. The showcase's vulnerability tile and posture sentence use the same state and wording; "scan pending" is retired, and a repository whose only findings are closed or about its own package no longer reads as pending. Run `aveloxis generate-showcase` after the start if you publish the showcase. See [Web GUI](../guide/web-gui.md), "The repository page's vulnerability tile". A fleet already running 0.29.199 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.199 marks every SBOM with the coverage it was made under; no migrate step, no setting.** Both formats gain a coverage marker (CycloneDX `metadata.properties` named `aveloxis:coverage:*`; an SPDX document `comment`), and a CycloneDX finding whose version is not determined gains the property `aveloxis:version_not_determined`. Stored SBOMs gain the marker as each repository is next collected; exports generated on request have it at once. See [REST API](../guide/api.md), "Changes for API clients in 0.29.199". A fleet already running 0.29.198 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.198 stops reporting an unknown libyear as 0; no migrate step, no setting. API clients that do arithmetic on `libyear` must read this.** In `GET /api/v1/repos/{id}/deps` (and `/libyear`), `libyear` is now `null` when it is not known, with `libyear_status` saying why; until now it was 0, which reads as "up to date". Every row also carries `scope`. The licences answer gains `left_out`, and the dependency snapshot says how many unknowns it skipped. See [REST API](../guide/api.md), "Changes for API clients in 0.29.198". A fleet already running 0.29.197 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.197 sends the coverage state from the API; no migrate step, no setting.** The vulnerability list answer and both statistics answers carry a `coverage` object: whether the repository's dependencies were read and checked, in one of nine states, with whether a count should be shown blank and whether "no vulnerabilities" may be said. One function decides it for every answer. Nothing is removed. See [REST API](../guide/api.md), "Changes for API clients in 0.29.197". A fleet already running 0.29.196 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.196 sends each finding's class, evidence and closing reason from the API; no migrate step, no setting.** `GET /api/v1/repos/{id}/vulnerabilities` adds `class` and, where they apply, `evidence` and `closed_reason` to every finding, and splits `counts.resolved` into `resolved_unlabelled` and one key per closing reason. Nothing is removed and no existing key changes its meaning; `resolved` is still the total of closed findings. See [REST API](../guide/api.md), "Changes for API clients in 0.29.196". A fleet already running 0.29.195 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.195 records the repositories a Gradle build declares; no migrate step, no setting. With `declared_repository_fetch` on, `serve` may contact them.** The entries of Gradle `repositories { }` blocks are now recorded in `repo_declared_repositories` like a pom's, with `google()`, `mavenCentral()` and `gradlePluginPortal()` standing for their addresses. A platform's BOM that the configured repositories do not have is then asked of the build's own https repositories, under the same rules as a pom's declared repositories (on by default, never a distrusted host, results stored). `mavenLocal()`, `flatDir`, `ivy`, `jcenter()`, plain-http addresses and addresses with credentials are recorded with the reason and never fetched from. This is what lets an Android build's BOM, which lives on Google's repository, be read. A fleet already running 0.29.194 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.194 gives Gradle dependencies the versions their platforms manage; no migrate step, no setting. `serve` fetches BOMs for Gradle builds from the configured Maven repositories.** A Gradle dependency written with no version (`implementation 'g:a'`) under a `platform(...)`, a Spring `mavenBom` import, or the Spring Boot plugin with dependency management now takes the BOM's version, read as a pom's imported BOM is, with `version_source` `managed`. The BOM is fetched from `collection.maven_repositories` under the same rules as Maven's (stored, bounded, never from a distrusted host). A platform that was applied leaves the inventory with a note; its findings close as `never_applied`. A dependency whose platform could not be obtained says why. On the sample of 53 Gradle repositories, 234 of 759 version-less dependencies sit under a BOM with a known version; how many resolve depends on the BOMs. A fleet already running 0.29.193 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.193 reads the rest of a Gradle build; no migrate step, no setting. Gradle repositories' dependency lists change again at their next analysis.** Versions and name parts held in `gradle.properties`, `settings.gradle`, a build file above, a file applied with `apply from:`, a version catalogue (`gradle/*.versions.toml`, with accessors such as `libs.guava`) or `buildSrc` constants are now read, in the clone only. Expect more rows (dependencies written as catalogue accessors, and coordinates whose name held a variable) and more versions known. On the sample of 53 Gradle repositories, rows with a usable version rose from 43.8% to 54.9%. See [Analysis](../architecture/analysis.md), "Gradle build files". A fleet already running 0.29.192 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.192 reads Gradle build files properly; no migrate step, no setting. Gradle repositories' dependency lists change at their next analysis.** Until now a `build.gradle` was matched line by line: one notation, seven configurations. It is now read as tokens: every configuration, map and Kotlin notations, `platform(...)`, and versions held in a variable the file assigns. At each Gradle repository's next analysis expect: new rows (annotation processors, `kapt`, `classpath`, variant and custom configurations, map notation); versions that were stored as an expression (`$springVersion`) now either read or left unknown; dynamic versions (`1.+`) unknown; entries of `constraints { }` blocks gone. Findings follow the versions: some open (a version is now known), some close with a reason (`version_determined`, `version_lost`), none as a fix. See [Analysis](../architecture/analysis.md), "Gradle build files". A fleet already running 0.29.191 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.191 adds the threat-list signal to the repository host check; no migrate step; one new setting.** Once a pass `serve` downloads a public list of host names reported as malicious (`collection.repository_host_threat_list_url`; by default the Phishing.Database project's list of active domains, about 11 MB, from `raw.githubusercontent.com`) and matches the repository hosts against it locally; no repository host is sent anywhere. A match is listed on the Repository hosts page as a hint, never a verdict. Set the setting to an empty string to turn it off. A fleet already running 0.29.190 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.190 adds the registration-date signal to the repository host check; no migrate step; one new setting.** For each repository host that has answered, `serve` now also asks the domain's registry, through the public registration-data service (RDAP), when the domain was registered; a date later than the first fetch from the host is listed on the Repository hosts page. This contacts `data.iana.org` and the registration-data servers it names, over https under the outbound-address rule, and discloses each domain only to the registry that already holds it. `"repository_host_registration_check": false` turns it off. See [Security](../guide/security.md), "The repository host check". A fleet already running 0.29.189 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.189 starts a periodic check of the package repository hosts; the migrate adds one table; one new setting.** Once every `collection.repository_host_check_hours` (24 by default, `0` for off) `serve` resolves each repository host's name and completes one TLS handshake with it, and records whether the name still resolves, whether it resolves to an address Aveloxis reaches, and whether its certificate is valid. Hosts with a signal are listed first on the administrator's Repository hosts page, under "Needs a decision". The check never distrusts a host and changes no collected data. The first pass begins when `serve` starts. See [Security](../guide/security.md), "The repository host check". A fleet already running 0.29.188 needs only the stop, the migrate and the start.

**0.29.188 adds the Repository hosts page to the administrator console; no migrate step, no configuration change.** `/admin/repository-hosts` lists the hosts Maven poms are fetched from with what depends on each, and distrusts or restores one, each behind its own confirm page. See [Web GUI](../guide/web-gui.md), "Administration". Only `aveloxis web` changes behaviour; a fleet already running 0.29.187 needs only the stop, the migrate (which has nothing new to do) and the start.

**0.29.187 adds the operations behind the repository-hosts page; the migrate builds one index. Nothing you can see changes.** The administration layer can now list the package repository hosts with what depends on each, say what distrusting one would do, distrust it (which also deletes what is stored from it), and restore it. Each is administrator-only and logged with who did it. The console page that uses them is the next release. The migrate builds `idx_repo_deps_libyear_version_hosts` `CONCURRENTLY` (a small partial index: only rows whose version came through a fetched pom). A fleet already running 0.29.186 needs only the stop, the migrate and the start.

**0.29.186 adds the list of repository hosts you have decided not to use; the migrate adds one table. Nothing changes until a host is put on it.** `aveloxis_ops.distrusted_repository_hosts` is empty after the migrate, and nothing puts a host on it by itself. Once a host is listed, nothing is fetched from it and nothing it served earlier is used: at each affected repository's next analysis a dependency whose version came through that host has no version, with `version_reason` `inherited_repository_refused`, and a Maven dependency whose only repository is listed keeps its row and says the same (never "not on a registry"). The administrator page that lists, distrusts and restores hosts follows in a later release; until then the table can be written by hand. A fleet already running 0.29.185 needs only the stop, the migrate and the start.

**0.29.185 records which repository hosts each Maven version came through; the migrate adds one table and two columns. Nothing you can see changes.** A Maven version worked out from fetched poms depends on the hosts that served them: a parent from one, a BOM from another. Each dependency row now carries those hosts (`repo_deps_libyear.version_hosts`), each Maven tree's are in `repo_dependency_coverage.maven_tree_hosts`, and `aveloxis_ops.package_repository_hosts` lists every host that has answered, with when it first did. **0.29.146 sidelines a dead API key and names keys in the log; nothing to configure, no schema change.** A key whose token is revoked or expired used to be rested and retried for as long as `aveloxis serve` ran: three 401s, a rest of up to 30 minutes, and again. **0.29.81 credits a merged contributor's commits to the contributor it was merged into.** Top contributors read from the daily commit table used to drop the commits of a contributor that a merge had folded into another. No schema change: from 0.29.80 the upgrade is the stop, `aveloxis migrate --skip-views` and the start.

**0.29.80 keeps a quiet collection with a broken clone incremental.** An incremental GitHub or GitLab collection whose clone fails and whose API phase found nothing new now completes with the clone's error in `last_error`, instead of failing as "no data collected", so the next collection stays incremental while you fix the clone. A first or forced collection is still judged and still fails that way. No schema change: from 0.29.79 the upgrade is the stop, `aveloxis migrate --skip-views` and the start.

**0.29.79 marks a repository's daily commit counts incomplete when a collection adds commits it could not record completely.** The page then reads the commits table for that repository until its next clean collection, instead of leaving the new commits out. No schema change: from 0.29.78 the upgrade is the stop, `aveloxis migrate --skip-views` and the start.

**0.29.78 keeps two answers with the response cache off.** With `api.response_cache_mb` unset (the default), the API again keeps the weekly time series and the top contributors in memory, up to 1,000 answers, as it did before 0.29.73; every other answer stays uncached until the setting is turned on. No schema change: from 0.29.77 the upgrade is the stop, `aveloxis migrate --skip-views` and the start; from an earlier version, follow the checklist, which includes 0.29.77's steps.

**0.29.77 builds two indexes and sets a storage parameter.** The top-contributors issue and pull-request arms read a large repository's rows one heap page at a time (repository 94609 on the production fleet: 505K pull-request rows and 58K issue rows, 2.5M page reads with the review and message arms, past nginx's 120 s). The migrate builds `idx_issues_repo_created_reporter` and `idx_pull_requests_repo_created_author` CONCURRENTLY — the v0.27.4 `(repo_id, created_at)` indexes with the author column INCLUDED, so those arms are index-only; the plain forms are dropped — and sets `autovacuum_vacuum_insert_scale_factor = 0.01` on the five large tables, because an index-only scan is only as good as the visibility map and insert-mostly tables left half their pages unmarked under the default. The ladder then runs, after the start and once serve is up, one manual `VACUUM (ANALYZE)` on messages, pull_request_reviews, pull_requests and issues to catch the map up (online; its duration scales with the table sizes and is not measured; a migrate that runs DDL — `aveloxis migrate`, or a serve start whose stamp is behind the binary — waits behind it per table, while a serve start on a stamped fleet fast-paths past the DDL). Run the ladder as usual.

**0.29.76 changes nothing in the schema.** After the fleet-wide `heal-commit-daily`, the repository page's `/stats` still answered 503 on the largest repositories: its last-activity bound fell back to a live scan of the commits table whenever the stored bound could not be used — not yet filled (it fills at the repository's next collection), or bogus and so read as unfilled (every kernel fork carries one commit dated 2085 and some one dated at the epoch; the next walk repairs the stored value). The activity bounds now read the first and last plausible day of the complete daily picture before any live scan. Run the ladder as usual.

**0.29.75 adds one column** (`repos.commit_daily_complete_at`, nullable, an instant ALTER) and, on the run that adds it, stamps every repository that already has daily commit rows (one indexed probe per repository; seconds on a fleet). From here the repository page's commit readers use the daily table only for a stamped repository — a facade walk whose every commit was proven written stamps it, `heal-commit-daily` stamps what it fills, a walk that swallowed writes never does — and `heal-commit-daily` lists the unstamped ones; a repository whose only walk swallowed writes shows the fuller commits table until its next clean walk. Also: every answer that depends on who asks — the routes behind a signed-in session, a signed-in caller's search, compare or entity search, the one-time Shared-with-Me notice, and every `401`/`403` — carries `Cache-Control: private, no-store` (`/api/v1/me` was the one Copilot named). Run the ladder as usual.

**0.29.74 changes nothing in the schema.** It exists so that every cached repository answer is recomputed: the answers' validators carry the binary's version, and 0.29.73's late fixes — the daily commit table's readers and the plausible-date bounds — changed answers without changing it, so a restart on 0.29.73 kept serving an old time series as a 304. Run the ladder as usual; a fleet that skipped 0.29.73 gets its steps.

**0.29.73 adds a column and a table** (`repos.data_changed_at`, stamped
by every writer of a repository's data so the API's response cache can tell
a changed repository from an unchanged one; and `repo_commit_daily`, the
facade's daily commit counts that the repository page's commit answers
read): run `aveloxis migrate --skip-views` on the way to it; `api` and
`web` refuse to start until the stamp is current. Then `aveloxis
heal-commit-daily --apply` (row 20) fills the new table for repositories
collected before — a background job, not a gate.

An older `aveloxis.json` keeps working: unknown keys are ignored and
every new key takes its documented default (see
[Configuration](configuration.md)) — with one class of exception: a value
a release starts to **validate** is refused at load, by `aveloxis migrate`
and every process alike, so check the table before step 3. Defaults that
**changed**, and values now refused — check whether you relied on the old
behavior:

| Key | Old default | New default | Since |
|---|---|---|---|
| `collection.scancode_shutdown_grace_minutes` | 30 | 0 — scancode subprocesses are killed immediately on `aveloxis stop` | v0.23.7 |
| `collection.pr_child_mode`, `collection.listing_mode` | `rest` | `graphql` (REST stays available as an escape hatch) | v0.26.0 |
| `collection.matview_rebuild_day` = `"disable"` | silently fell back to Saturday | honored (alias of `disabled`) | v0.27.96 |
| `collection.vuln_scan_transitive` | off | on — lockfile closures + transitive findings + real SBOM graphs | v0.27.136 |
| `collection.archived_recollect_multiplier` | (every repo on the same cadence) | 6 — archived repos recollect six times less often | v0.28.1 |
| `api.trusted_proxy` | any text; a host name, a CIDR or a non-canonical spelling silently never matched | must be an IP address in canonical form (`127.0.0.1`, lowercase compressed IPv6); anything else is **refused at load**, naming the canonical spelling | v0.29.73 |
| `api.front_end_secret` | — | a value without `api.trusted_proxy`, or shorter than 32 characters, is **refused at load** | v0.29.73 |

Two behavior changes that need no configuration but are worth knowing:
since v0.27.139 incremental collection anchors `since` on the previous
round's `last_collected` (the pre-v0.27.139 `now − days_until_recollect`
window silently skipped items last-updated between rounds), so the first
post-upgrade cycle per repo is transitional and `heal-collection-gaps`
below covers the history; and path values in `aveloxis.json` are never
`$HOME`-expanded — use absolute paths.

### The v0.26.3 event-cohort SQL

Before v0.26.3 the issue-event and PR-event feeds paginated the same
GitHub endpoint twice; on any repository where nothing changed between
the two passes the second one got a 304 and the entire PR-event history
was silently dropped. "Has PRs but no PR events" can be legitimate for
small quiet repos, so this is deliberately *not* an automatic migration.
Flag the affected cohort for one full recollect (lower the `HAVING`
threshold to taste):

```sql
UPDATE aveloxis_ops.collection_queue q
SET force_full_collect = TRUE
FROM (
    SELECT pr.repo_id
    FROM aveloxis_data.pull_requests pr
    WHERE NOT EXISTS (SELECT 1 FROM aveloxis_data.pull_request_events e
                      WHERE e.repo_id = pr.repo_id)
    GROUP BY pr.repo_id
    HAVING COUNT(DISTINCT pr.pull_request_id) >= 50
) sub
WHERE q.repo_id = sub.repo_id
  AND q.force_full_collect = FALSE;
```

Each flagged repo re-walks its full event history on its next cycle.

### Mailing lists on an existing catalog

`aveloxis load-apache-lists` never inserts repositories. For each Apache
PMC it looks the PMC's primary repository up in your catalog (URL
variants first, then a github.com redirect probe for renamed projects)
and registers that PMC's lists only when the repository is found;
everything else is counted as skipped. On a catalog that already holds
some Apache repositories it therefore registers exactly those PMCs —
`load-foundation-core-repos` is only needed if you want every PMC's
flagship repository imported first. A PMC whose *sibling* repository you
track (say `apache/arrow-rs` without `apache/arrow`) is skipped, because
mailing-list bodies attach to the PMC's primary repository. The command
needs outbound network access (Apache's `projects.json` /
`podlings.json`, `lists.apache.org` for list enumeration, and github.com
for the redirect probe) and moves each linked repository into an
`Apache PMC: <slug>` repo group.

```bash
aveloxis load-apache-lists --dry-run   # [pmc] list → repo_id per PMC you hold; the rest are "skipped"
aveloxis load-apache-lists
```

Then enable the worker in `aveloxis.json` and restart `serve`:

```json
{
  "collection": {
    "mailing_list_enabled": true,
    "mailing_list_polite_email": "you@example.org",
    "mailing_list_backfill_months": 6
  }
}
```

`mailing_list_polite_email` is the contact address sent to the archive
admins in the `User-Agent`; `mailing_list_backfill_months` bounds the
first pass per list (`0` = full history from each list's first month).

`aveloxis mailing-list-stats` shows coverage as lists drain;
`aveloxis verify-mailing-list` reports which classification and routing
branches have produced rows. Run the mailing-list ingestion *after* the
issue / PR heals above have settled: messages are projected onto the
issues and pull requests already in the database, so a more complete
catalog links more mail. Full design in
[Mailing-List Ingestion](../architecture/mailing-list.md).

## Recurring maintenance (not tied to a release)

A few checks are worth a calendar entry rather than an upgrade step. All
but one run only when you run them; each exists because a fleet drifted
without anyone noticing.

| Cadence | What | Why |
|---|---|---|
| quarterly, and after any incident where someone raised a limit | run the `pg_settings` verification query in [Verifying what is actually live](../guide/scaling.md#verifying-what-is-actually-live) and diff it against your recorded baseline | the settings that OOM a host (`work_mem` × `max_connections` × parallel workers) are the ones most often raised "temporarily" — see [Drift is the failure mode](../guide/scaling.md#drift-is-the-failure-mode) |
| automatic since v0.29.7 (`collection.gone_repo_recheck_days`, 28) | `aveloxis serve` re-probes every "gone" repository once per cadence and re-enqueues the ones that answer 2xx; `aveloxis mark-gone-repos` is the on-demand form | a repository that returned 404/410/451 was **dequeued**, so no collection cycle ever looks at it again, and organizations do flip repositories private and back. On a release before v0.29.7 run the command quarterly by hand. The probe is an unauthenticated HEAD per candidate — it spends no API budget |
| quarterly | `aveloxis reconcile-repos` | stranded `repos` rows left by upstream renames (row 10 above) accumulate between upgrades too |
| yearly, or when disk is tight | index audit before dropping anything: `SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) FROM pg_stat_user_indexes WHERE relname = 'commits' ORDER BY idx_scan;` | zero-scan indexes on `commits` can reach tens of GB, but the matview `UNIQUE` indexes read as zero-scan and are REQUIRED for `REFRESH ... CONCURRENTLY` — audit readers first, drop only email/affiliation indexes nothing queries |
| once, then whenever the network changes | confirm `pg_hba.conf` does not carry a `host all all 0.0.0.0/0` line for a port that is reachable from the internet; firewall the port or restrict it to known networks | the PostgreSQL log's `password authentication failed` lines from unknown addresses are the symptom |

If you run more than one host against the database, the second host's
role is a decision, not an accident — see
[Dedicated scancode host](../guide/dedicated-scancode-host.md).
